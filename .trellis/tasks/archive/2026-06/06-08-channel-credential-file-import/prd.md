# 渠道创建页支持凭证文件批量导入

## Goal

在默认前端的渠道创建抽屉中增加“凭证文件批量导入”能力，让管理员可以选择一个 zip、一个 JSON 文件或多个 JSON 文件，将其中的账号凭证转换为多个渠道。导入时复用当前创建渠道页面上的模型、分组、代理、标签、权重、状态等配置；渠道名自动使用凭证中的账号名；渠道类型优先使用 JSON 中声明的渠道类型，缺失时默认 Codex。

## What I already know

- 用户要求入口在“渠道页面的创建渠道”中，不是离线脚本。
- 文件输入支持三类来源：单个 `.json`、多个 `.json`、一个 `.zip`（包含 JSON 凭证）。
- 渠道名应使用账号名；现有 Codex 创建逻辑在渠道名为空时用 `email` 作为名称。
- 渠道类型从 JSON 中读取；没有类型时默认 Codex（后端常量 `ChannelTypeCodex = 57`）。
- 其他配置仍由页面表单配置，包括 models/group/test_model/proxy/tag/priority/weight/status 等。
- 现有前端路径：`web/default/src/features/channels/components/drawers/channel-mutate-drawer.tsx`。
- 现有前端已经有 Vertex AI 的 JSON 文件上传输入，可复用 UI/交互模式。
- 现有前端提交路径：`transformFormDataToCreatePayload` 生成 `AddChannelRequest`，`createChannel()` POST `/api/channel`。文件导入可复用该 payload 形状，作为 multipart 中的配置字段。
- 现有后端 `controller.AddChannel` 已支持 `mode=batch`，并对 Codex JSON 数组执行 `getCodexBatchKeys()`。
- 现有后端 `getCodexChannelName()` 已在名称为空时从 `email` 取渠道名；需要扩展为“每个文件/凭证独立渠道名”，避免同一批导入时一个表单 name 覆盖所有渠道。
- 现有 i18n 已包含上传相关通用键；新增 UI 文案需要同步 `en/zh/fr/ja/ru/vi`。
- shadcn 项目上下文：React 19 + TypeScript，Tailwind v4，Base UI 风格，组件别名 `@/components/ui`。

## Assumptions (temporary)

- “账号名”优先使用 JSON 中的 `email`；如果没有 `email`，再尝试常见字段如 `account_name` / `username` / `name`；仍没有则使用 `codex-<随机/序号>`。
- JSON 中的“渠道类型”可能是 `type`，值可能为数字（`57`）或字符串（`codex` / `chatgpt` 等）。MVP 至少支持数字类型与 `codex` 字符串。
- 推荐使用后端 multipart 导入接口解析文件：前端只负责选择文件和提交表单配置，后端用 Go 标准库解析 zip/json，不新增前端依赖。
- 复用现有 `AddChannelRequest` / `BatchInsertChannels` 语义；新增接口只负责把上传文件转换为一组待创建渠道。
- 批量文件导入只用于创建新渠道，不用于编辑已有渠道。

## Open Questions

- 当前无阻塞问题；默认采用后端 multipart 导入接口，避免新增前端 zip 依赖。

## Requirements (evolving)

- 在创建渠道抽屉的认证/密钥区域增加“从凭证文件导入”入口。
- 支持选择：单个 JSON、多个 JSON、单个 ZIP。
- JSON 文件可以是单个凭证对象，也可以是凭证对象数组。
- ZIP 内递归读取 `.json` 文件，忽略目录和非 JSON 文件。
- 每个凭证对象生成一个渠道。
- 渠道名按凭证中的账号名自动填充；不再要求用户手动输入一个会覆盖所有渠道的名称。
- 每个凭证对象的渠道类型优先从 JSON 读取；缺失时使用 Codex。
- 页面上的其他配置作为批量导入默认配置应用到所有生成渠道。
- 导入前端应显示解析数量/错误，并避免把 token 明文显示在 toast 或日志中。
- 后端应校验每个渠道类型对应的 key 格式，并保持已有 `BatchInsertChannels` 事务语义。
- 新接口应限制文件数量、单文件大小和 zip 解压总量，避免 zip bomb / 超大请求。

## Acceptance Criteria (evolving)

- [ ] 管理员在创建渠道抽屉可选择 `.json` / 多个 `.json` / `.zip` 凭证文件。
- [ ] 选择有效文件后，表单进入批量创建模式并能创建对应数量渠道。
- [ ] Codex 凭证 JSON 缺少类型时创建为 type 57。
- [ ] JSON 中存在有效类型时按该类型创建渠道。
- [ ] 渠道名来自凭证账号名（优先 email），不是统一表单名。
- [ ] 页面配置的分组、测试模型、模型列表、代理等字段被应用到导入渠道。
- [ ] 错误文件能给出文件名和原因，不泄露 token。
- [ ] 后端单元测试覆盖 JSON 对象、JSON 数组、zip/multiple files、mixed type/default codex、缺失必填字段。
- [ ] 前端 typecheck/lint 通过；后端相关 Go tests 通过。

## Proposed Design

### Recommended approach

Add a new admin-only endpoint such as `POST /api/channel/import` that accepts multipart form data: one `payload` field containing the same channel configuration generated by the create form, plus one or more `files` fields containing `.json` or `.zip` files. The backend parses files into credential objects, applies per-object type/name overrides, then calls existing validation and `model.BatchInsertChannels` in one transaction. The frontend adds a file input in the create-channel drawer, shows parsed/import status, and submits to the import endpoint when files are selected.

### Alternatives considered

1. Frontend-only parsing with JSZip: simpler backend, but adds a dependency and handles zip parsing/token material in browser code. Rejected for now because project policy prefers no new dependencies unless explicitly needed.
2. Reuse existing `/api/channel` JSON-only batch endpoint by converting files to JSON arrays in frontend: works for multiple JSON files but not zip without dependency. Rejected because zip is a required input format.
3. Backend multipart import endpoint (recommended): uses Go standard library, centralized validation, no new frontend dependency, and can enforce zip safety limits.

### Data flow

User selects files in create drawer → frontend submits current create-form config + files → backend extracts JSON credential objects → each object resolves channel type and channel name → backend validates and inserts channels/abilities → frontend invalidates channel list and closes drawer.
